# 썰집 마스터 프롬프트·서버 반영 검토

검토일: 2026-09-10. 이번 첨부는 변경요약을 포함한 새 버전이며, 앞선 인물 강제 변경·여담 삽입·문장 글자 수 할당·값 존재만으로 길이 요청을 인정하는 규칙이 정리되었습니다. 서버 자동 절단 제거는 문서상의 요구사항이며 현재 사이트에서 실행 완료된 상태는 아닙니다.

## 1. ‘충분히 전달하면 끝낸다’의 판단 가능성

현재 문장은 모델이 방향을 판단하는 데 사용할 수 있습니다. 다만 ‘핵심’과 ‘충분’의 선택이 모델마다 달라질 수 있으므로 글자 수 대신 원문 근거와 장면의 역할을 명시하는 것이 좋습니다.

추가 권장 문구:

> 작성 전에 원문에서 사건을 일으킨 계기, 인물의 행동과 그 결과, 중요한 말이 상황을 바꾸는 지점, 감정이 바뀌는 이유, 마지막에 드러난 사실을 파악한다. 어떤 장면을 빼면 원인과 결과를 이해하기 어렵거나 대사의 의미·결말의 해석이 달라진다면 그 장면의 전개와 반응을 남긴다. 이 요소들이 결과 본문에서 연결되어 이해되고, 설명되지 않은 핵심 연결이 없으면 끝낸다. 원문 자체가 미해결로 끝났다면 미해결 상태를 유지한다. 원문에 없는 동기나 해답을 보충해 완결시키지 않는다. 원문과 결과의 글자 수·문단 수·대사 수를 맞추지 않는다.

이는 내부 작성 기준입니다. 체크리스트나 중간 추론을 13개 결과 필드에 추가할 필요는 없습니다. 원문에 이미 있는 회상이나 후일담이 사건 이해에 중요하다면 보존 대상입니다. ‘불필요한 회상·후일담을 추가하지 않는다’가 기존 회상까지 지우라는 뜻으로 읽히지 않게 해주세요.

남은 충돌:

- master의 ‘설명이 끝난 자리에서 끊지 않는다’는 절대 금지입니다. 짧은 원문에 다른 전환점이 없으면 기존 내용 보존과 충돌합니다. 문장 경계의 자연스러움을 우선하고 분할 불가 시 후보 보관/분할 검토 상태를 별도 계약으로 정의해야 합니다. 두 본문을 비우지 못하는 현재 스키마와 함께 설계해야 합니다.
- ‘원문의 서술을 대사로 옮긴다’는 실제 발화가 없었던 내적 생각을 특정 인물의 발언으로 만들 수 있습니다. 발화 주체·확신 수준·상대에게 전달됐는지가 달라지면 서술로 유지한다는 예외가 필요합니다.
- AI 문체 목록의 형용사 개수·절 개수 제한은 여전히 수치 규칙입니다. 본문 총분량 규칙은 아니지만 원문 보존보다 우선하지 않도록 해야 합니다.

## 2. lengthMode / lengthRequest의 실제 diff

patches/01-length-options.patch에 현재 커밋 기준의 적용 가능한 diff가 있습니다. 테스트에서는 실제 patch를 적용한 파일을 import해 확인했습니다.

흐름:

| 단계 | 처리 |
|---|---|
| cleanDraft | 옵션 화이트리스트에 lengthMode를 넣고 custom + 유효한 문자열일 때만 lengthRequest 보존 |
| promptFor | 서버와 동일한 정규화를 다시 수행하고 생성·부분 수정에만 lengthRequest 전달 |
| UI collect | 기존의 명시적인 요청을 보존. 구버전 length를 되살리지 않음 |
| 모델 컨텍스트 | action과 유효한 target을 JSON에 명시 |
| rewrite 요청 | 누락·잘못된 target을 before로 바꾸지 않고 거절 |

서버 문서 1번은 options.length 제거라고 하고 2번은 ‘호환용으로 유지한다면’이라고 합니다. 계약을 ‘legacy length 폐기, lengthMode/lengthRequest만 사용’으로 통일하는 것이 좋습니다.

mode와 request는 사용자 클릭의 암호학적 증거가 아닙니다. UI가 실제 조작 시에만 custom을 저장해야 하고, 구버전 데이터 이관 시 숫자를 문구로 바꾸거나 custom으로 자동 승격하지 않아야 합니다. 현재 기본 화면에 분량 UI가 없으므로 새 토글은 추가하지 않았습니다. 직접 요청은 기존 notes/rewriteInstruction으로도 전달됩니다.

옵션 diff는 sourceText/본문의 기존 절단을 제거하는 전체 정책 패치가 아닙니다. 두 작업의 적용 범위를 구분했습니다.

## 3. social 보정에는 본문 전체를 전달

기본값은 완성된 beforeContent와 afterContent 전체를 그대로 보내는 것입니다. 요약은 핵심 대사·관계·반전의 조건을 누락할 수 있고, 본문에 실제로 존재하는 coverDetail을 고르는 검사도 약화됩니다. 요약 생성 자체에 추가 호출이 들 수 있습니다.

보정 요청에는 아래를 전달합니다.

- action=social, intent=repair
- 고정 title, category, beforeContent, afterContent
- 기존 social 다섯 필드
- allowedFields와 서버가 확인한 필드별 오류
- 서버에 보관할 원고 revision과 컨텍스트 hash

소재 원문·OCR·본문 축약 요청·원본 이름이 든 storyBible은 필요하지 않습니다. 모델은 원고 결말을 알아야 부가 문구에서 결말을 숨길 수 있으므로 afterContent도 보냅니다.

출력 도구는 기존 다섯 필드 스키마를 유지합니다. 적용 시 allowedFields만 복사합니다. ‘해시태그 보정’에 모델이 hook/caption을 바꿔 보내더라도 기존 값을 유지합니다. title은 수정할 수 없으므로 titles 보정 시 고정 title을 후보에 포함해야 합니다.

src/social-repair.mjs 구현 내용:

- 원문을 자르지 않는 전체 본문 컨텍스트 구성
- 정해진 다섯 필드만 허용하는 응답 검사
- 선택한 필드의 개수·포함 관계·표지 인용·용량 검사
- hook 권장 줄 수는 경고 처리
- revision과 컨텍스트 hash가 바뀌면 보정 적용 거절
- 한 번만 호출하는 어댑터와 max_tokens/컨텍스트 한도 중단 처리
- 본문과 지정하지 않은 필드를 보존한 candidate 반환

DB 저장 직전에는 revision 조건을 포함한 원자적 갱신이 추가로 필요합니다. 서버가 같은 상태를 검사하고 저장하도록 해야 합니다. 후보 저장과 실제 API 연결은 모듈 바깥의 통합 작업입니다.

현재 validateResult('social')는 응답을 먼저 잘라 반환합니다. 이 함수를 보정 어댑터 앞에 두면 초과 오류가 사라지므로 raw tool input 추출과 필드 검증을 분리해야 합니다.

한도를 넘는 본문은 자동 요약하지 않습니다. 서버 저장소에서 전체 본문을 조회해 요청하고도 모델 컨텍스트에 들어가지 않으면 용량 문제로 처리합니다. 긴 본문용 근거 추출 방식을 추가하려면 별도 기능으로 설계하고 원문 전체와 같은 정확성을 보장한다고 표현하지 않아야 합니다.

## 4. 자동 절단 목록의 누락·구체화

상위 함수명으로 묶인 경로는 있지만 개별 호출점을 명시해야 누락을 막을 수 있습니다.

| 추가 확인 지점 | 현재 코드/문서 문제 | 조치 |
|---|---|---|
| URL readSource 끝 | 표에는 100자 미만 거절만 쓰였으나 같은 함수에 slice(0,50000)도 존재 | 최소 길이 거절과 최대 길이 절단을 각각 처리 |
| validateResult('extract') | string(r.text,50000)으로 추출 결과가 잘림 | 추출 결과 원본을 보관하고 용량 오류를 분리 |
| validateResult('generate') | imageText를 sourceText에 최대 8000자로 복사 | 표시 발췌가 원문을 대체하지 않게 변경 |
| cleanDraft의 imageIds | slice(0,8)로 첨부 ID 초과분 폐기 | UI는 이미 초과를 거절하지만 서버 직접 요청도 명시적으로 거절해야 함 |
| 새 OCR 원문 필드 | cleanDraft는 화이트리스트 외 필드를 모두 버림 | 원문 저장소·참조 ID·버전·수집 완료 상태의 실제 영속 경로 구현 |
| review 응답 | issues.slice(0,20)로 문제 후보 일부를 제거 | 전체 보관 또는 표시용 페이지 처리. 본문 절단과 구별 |
| string의 개행 변경, split의 trim/filter | 범위 밖 공백·개행 보존 요구와 충돌 가능 | 기준 원문 작성 이후 내용 정규화 금지. split은 문단 위치 기반으로 분할 |
| 요청 바이트 한도 | JSON 전체를 350000바이트에서 거절. 개별 필드 허용량과 합산 요청량은 다름 | 필요 데이터만 전송하거나 서버 ID 조회. 내용 축약을 요구하는 오류 안내 수정 |

자동 저장/복원/게시/미리보기와 HTML maxlength도 기존 표대로 함께 맞춰야 합니다. build.py로 만드는 public/studio/index.html 등의 산출물도 재생성해야 합니다.

유지해도 되는 slice: 목록 20개 페이지 처리, 다음 글 목록, 그라데이션에만 쓰는 앞 문단 발췌, 원문 근거 표시용 substring입니다. 이들은 전체 본문을 따로 보존하고 있으므로 원문 절단과 구분합니다. 이미지 헤더의 바이트 시그니처 검사도 삭제 대상이 아닙니다.

문서의 ‘100자 미만이면 사용자에게 확인’은 짧다는 이유로 매번 중단시키는 대체 규칙이 될 수 있습니다. 정상적으로 추출된 짧은 원문은 그대로 받으며, 글 대신 메뉴만 추출되는 등 수집 이상 징후가 있을 때 확인하는 쪽이 목적에 맞습니다.

## 5. 원문 보존 검사의 실제 구현과 범위

src/source-preservation.mjs와 실행 예제를 제공합니다.

| 항목 | 구현 | 범위 |
|---|---|---|
| 사건·인과 | 원문 근거 구간의 단어가 결과에 있는지 비교 | 어휘 누락 후보만 표시. 인과 반전은 판정하지 않음 |
| 인물 | 확인된 이름 대응표와 조사 경계를 고려한 등장 검색 | 원래 이름 잔존/대체 이름 미검출 후보. 동명이인 단순 대응은 거절 |
| 새 이름 | 외부 NER 또는 사람이 준 이름 후보의 실제 위치를 검증한 뒤 대응표 비교 | 한국어 이름 추출기는 포함하지 않음. 후보 미제공 시 미검사 |
| 대사 | 따옴표 구간 통계와 선택적 대사 근거 단어 비교 | 제목 인용도 따옴표에 들어가므로 실제 대사 수라고 단정하지 않음 |
| 감정 | not_checked 표시 | 문자열 검사로 감정 보존을 통과 처리하지 않음 |
| 반전·결말 | 명시적으로 지정한 결말 근거의 단어·수치를 비교 | 원문의 마지막 몇 %를 임의로 결말로 간주하지 않음 |

모든 후보는 severity=review이고 실패·자동 재생성으로 연결되지 않습니다. 결과는 semanticVerdict=undetermined입니다. 원문이 수집 미완료이면 비교를 건너뛰고 미완료 상태를 표시합니다. 근거 구간이 오래된 원문에 속하거나 원문 hash가 달라졌다면 기준 재확인을 요구합니다.

기본 입력 계약에는 원문에서 선정한 anchors, 확인된 people 대응표가 필요합니다. 13개 생성 결과만으로 이를 독립적으로 확보할 수는 없습니다. 이를 자동 생성하려면 원문 분석 단계 또는 별도 의미 비교 모델을 연결해야 하며, 생성 결과의 storyBible을 그대로 검증 정답으로 쓰면 안 됩니다.

중요한 제한: ‘사직서를 낸 적 없다’를 ‘사직서를 제출했다’로 바꿔도 사직서라는 단어는 남습니다. 이 사례에서 코드가 의미 보존 성공을 표시하지 않는 것을 테스트했습니다. 원문 보존 여부를 자동 확정하는 제품 기능으로 소개하면 안 됩니다.

## 추가 문서 정합성

- master는 imageText를 ‘이미지에서 읽은 본문’, 서버는 ‘표시용 발췌’로 설명합니다. 전체 판독 완료와 발췌 출력의 생략을 구분해야 합니다. 읽었지만 출력에서 생략한 내용은 미판독 내용이 아닙니다. 다만 이후 작업에도 그 전체 판독 결과가 실제로 보존돼 있어야 합니다.
- 현재 13개 생성 필드에는 OCR 전체 텍스트가 없습니다. 전체 저장을 하려면 원문 수집/OCR 단계에서 완전한 결과를 먼저 영속화하거나 응답 계약을 별도로 설계해야 합니다. 문서만으로 전체 OCR이 보관되지는 않습니다.
- social은 부가 필드 전체를 다루지 않습니다. title/category/teaser/gateLine 등의 오류는 해당 스키마로 고칠 수 없습니다.
- 필수 필드 오류를 통째로 실패 처리하면 비어 있는 hashtags 같은 복구 가능한 문제도 전체 생성 실패가 됩니다. 오류 위치와 종류로 분류하고, 부가 필드 오류의 maxLength 검사도 전체 후보 폐기 전에 분기해야 합니다. 최종 완성 결과의 스키마 제약을 완화할 필요는 없습니다.
- 동일한 rewrite 응답은 ‘변경 없음’이며 항상 재시도할 실패 신호는 아닙니다. 요청이 이미 충족된 경우도 있습니다.
- strict 도구 스키마를 ‘타입과 required만’으로 설명한 부분은 부정확합니다. properties/items와 객체의 additionalProperties:false가 필요합니다. minItems는 0 또는 1이 지원되므로 ‘전부 미지원’ 대신 사용하려는 제약별로 구분해야 합니다. 서버용 스키마의 문자열·배열 제약은 별도 검증합니다. [Anthropic Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- max_tokens는 요청에 설정된 출력 한도 도달이고, model_context_window_exceeded는 별도 중단 사유입니다. 무조건 토큰을 올리는 재시도 대신 모델이 허용하는 범위와 남은 컨텍스트를 확인하고 제한된 재시도 횟수를 정해야 합니다. 본문 자동 요약은 하지 않습니다. [Anthropic Stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)
